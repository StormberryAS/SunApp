# SunApp

Privacy-first solar-position calculator. SunApp computes precise sunrise, solar noon and sunset times for any location on Earth, handles timezone resolution, and addresses edge cases such as the Midnight Sun and Polar Night.

**Live:** [sun.stormberry.as](https://sun.stormberry.as)

## Features
- **City search**: rapid, offline autocomplete over 25,007 cities, accent-insensitive both ways (`tromso` finds Tromsø) and exonym-aware (`Gothenburg` finds Göteborg).
- **Android app**: the same calculations as a native app, with the Stormberry Labs carousel above its footer, as on the website. The Zapstore version also has optional alarms anchored to solar events. [Get it on Zapstore](https://zapstore.dev/apps/no.stormberry.sunapp) or [on Google Play](https://play.google.com/store/apps/details?id=no.stormberry.sunapp.play).
- **Manual GPS input**: find astronomical data for any arbitrary point on the globe. A decimal comma works as well as a point (`60,39` or `60.39`), and so does a typographic minus; anything out of range is refused with a message rather than computed.
- **Time travel**: pick any date, past or future, to calculate historical or upcoming solar events.
- **Polar edge cases**: displays "Midnight Sun" or "Polar Night" when applicable based on latitude and season.
- **Responsive layout**: optimised for mobile and desktop.

## Architecture
- **Vanilla HTML/CSS and TypeScript**, no frameworks and no runtime dependencies. The page code is written in TypeScript (`ts/app.ts`) and compiled to the plain `app.js` the page loads, which is committed, so GitHub Pages serves the repository as it is with no build step of its own.
- **Privacy first**, and precisely so: no cookies and no tracking. **The sun times themselves involve no network at all**: every city carries its own IANA timezone in the bundled catalogue, and a raw GPS coordinate is resolved to a zone by nearest-neighbour lookup in that same catalogue, so there is nothing to send and nowhere to send it. The page never asks for the device's location either: a place comes from city search or from typed coordinates. The only requests the web page makes are first-party icons for the app-switcher strip, served from stormberry.as. The **Android build makes none at all**: it declares no `INTERNET` permission, which makes that claim checkable rather than promised.
- Stormberry dark-mode glassmorphism design system, Inter typography.
- **Sovereign AI**, built and maintained using high-speed agentic workflows.

## Stack
- [SunCalc](https://github.com/mourner/suncalc) for solar position maths, bundled locally.
- Browser `Intl` API for timezone-aware time formatting.
- No third-party services. An earlier version called Open-Meteo to resolve raw coordinates to a timezone; that was replaced by an offline nearest-city lookup and the dependency is gone.
- [Inter](https://rsms.me/inter/) typeface (OFL 1.1), locally hosted, and bundled in the Android app.

## Local development
```bash
git clone https://github.com/StormberryAS/SunApp.git
cd SunApp
python3 -m http.server 8000
```
Open `http://localhost:8000` in your browser.

### Updating the city database
The city catalogue is generated by `update_cities.py`, which is shared with eight sibling Stormberry Labs apps and is the single source of truth for all of them. It draws population data from `geonamescache`, guarantees the top 10 cities per country, every US state capital, the top 5 per US state and every Brazilian capital, then fills to 25,000 by population, and finally adds a hand-maintained list of local places that fall below the cutoff. English exonyms come from GeoNames' own language-tagged alternate-names dump, so `Cologne` resolves to Köln. The result is packed into palettes plus tab-separated rows and written to every app as `cities.js`, and to `data/cities.tsv` for the Android build.

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install geonamescache
python update_cities.py
```
The `.venv` folder is excluded via `.gitignore` to keep the repository lightweight.

### TypeScript, build and tests
The page code is TypeScript: edit `ts/app.ts`, never `app.js`. `tools/build-ts.sh` compiles it with the pinned TypeScript 6.0.3 (strict) into `app.js`, a classic script like before, and then runs `bump_assets.py` so the page loads the new file under a fresh `?v=` stamp. `app.js` is committed, because GitHub Pages publishes the repository as it is; `.gitattributes` marks it as generated. The build refuses to overwrite an `app.js` edited by hand. `suncalc.js` (SunCalc 1.8.0, vendored, byte for byte) and `cities.js` (written by `update_cities.py`) are not compiled; their declarations live in `ts/`.

Needs Node 24 and Python 3. The tests are TypeScript too, run by Node directly.

```bash
tools/build-ts.sh            # npm ci (frozen, install scripts off), type-check, compile ts/ to app.js, stamp the page
tools/build-ts.sh --check    # change nothing; fail if app.js is stale, a stamp is stale or the city data disagree
npm test                     # unit tests: page helpers, golden corpus, city parity, day classifier, the TypeScript rule
npm run smoke                # the page in headless Chromium, against snapshots captured from SunApp 1.1.3
npm run sw-smoke             # the offline pilot's service worker in headless Chromium, under the real host name
node tools/gen-solar-golden.ts [--check]   # (re)write the Android port's solar golden corpus
```
`package.json`, `package-lock.json`, `.npmrc`, `tsconfig.json`, `tsconfig.sw.json`, `ts/`, `tests/`, `tools/` and `node_modules/` are development files only: `_config.yml` keeps them off the site, and the Android build copies only `data/cities.tsv`.

### Offline pilot (iPhone Home Screen)
A service worker (`ts/sw.ts`, compiled to `sw.js`) lets the site open with no network after one online visit, for the Home Screen web app on iPhone. It registers only on `https://sun.stormberry.as`, never on the onion mirror, on `localhost` or on any other host, and the Android app never loads the web page at all. While `OFFLINE_PILOT` in `ts/app.ts` is `'opt-in'`, only a visit to `https://sun.stormberry.as/?offline=1` installs it. Pages are fetched from the network first and fall back to the stored copy only when there is no network; scripts and stylesheets are stored under their `?v=` stamps, which `bump_assets.py` also writes into `sw.js`, so every release replaces the stored files. To switch it off, set `OFFLINE_PILOT` to `'off'` (every device drops it on its next visit) or `KILL` in `ts/sw.ts` to `true`, then build and deploy. Once the worker has shipped, never delete `sw.js` and never revert the pilot as a whole: a device keeps its worker while `sw.js` answers 404, and with `offlinePilot()` gone from `app.js` neither switch can reach it. To end the pilot, deploy `OFFLINE_PILOT = 'off'` and `KILL = true` together and keep both served for at least three months (a Home Screen app can go unopened for weeks); only then remove the code. If `sw.js` was removed by mistake, serving a `sw.js` with `KILL = true` again clears the worker at each device's next visit.
